Is tanaki/integration-contracts actually reusable, or does it just look that way?

Reviewed as if I had never seen this code before, with the explicit goal of breaking the reusability claim. Two real findings survived; neither is a code-coupling defect, and neither blocks reuse by another Laravel app or a non-Laravel PHP app.

00

Audit method

Every claim below is backed by a command actually run against the package as it sits on disk, not a re-read of the design documents that shipped it. Where a check produced a false positive from my own tooling, that's disclosed too — an audit that hides its own mistakes isn't independent.

Four categories of evidence were gathered: (1) static grep/reflection sweeps of src/ for forbidden references, (2) a component-wise, case-sensitive comparison of every namespace declaration against its actual on-disk directory — the specific failure mode that stays invisible during development on Windows (case-insensitive) and only surfaces on a case-sensitive Linux production filesystem, (3) a live execution test in a PHP process that loads only this package's own Composer autoloader — not Tanaki Hub's — to settle the non-Laravel question by demonstration rather than by argument, and (4) inspection of the package's own resolved vendor/ tree, which is the most honest witness available: if a hidden Laravel dependency existed, Composer's own resolver would have had to install it.

02

Hidden application dependencies — one real finding

grep for App\, BaseModel, MultiTenantScope, IntegratedDevice, or any Tanaki Hub class nameClean in code
2 matches, both inside doc-comments referencing "IntegratedDevice" as illustrative context for a reader (e.g. "recorded as metadata on IntegratedDevice for diagnostics/operations"). No import, no type-hint, no runtime reference. A genuinely external maintainer reading these two comments would learn about a foreign class name they've never seen — a minor documentation smell worth polishing, but not a dependency: nothing fails, nothing imports it, nothing requires it to exist.
Finding — a real, if narrow, leak: DriverNotFoundException's message assumes a Laravel-Artisan host

DriverNotFoundException::forVendor() returns: "No driver is registered for vendor key [{vendorKey}]. Run php artisan integration-engine:driver:discover if a new driver class was just added." This is not a code coupling — the exception constructs and throws correctly regardless of host — but it is a genuine hidden application assumption baked into user-facing text returned by the public API: it assumes (a) the host is Laravel, since non-Laravel PHP has no artisan at all, and (b) the host has a command literally named integration-engine:driver:discover, which doesn't exist in this package — it lives in Tanaki Hub's own application layer and hasn't even been extracted into integration-core yet. A different Laravel application integrating this package would see advice for a command it doesn't have. Confirmed via direct grep across all 4 exception classes — this is the only one of the four with this problem; DeviceOfflineException, InvalidPayloadException, and ProtocolNotImplementedException all have clean, host-agnostic messages.

04

Semantic versioning principles — followed

  • composer.json declares "version": "1.0.0" explicitly — correct and necessary here specifically because this project has no Git history to infer a version from (confirmed: no .git anywhere in the repository). Composer's own documentation names this exact scenario as the intended use of the version key; this is not a smell.
  • Both of the package's own dependency constraints (php: ^8.2, nesbot/carbon: ^3.0) use caret constraints — the SemVer-idiomatic choice, allowing compatible upgrades without a manual bump.
  • CHANGELOG.md follows Keep a Changelog structure with a dated 1.0.0 entry categorized under Added/Notes.
  • UPGRADE.md exists as a distinct document from the changelog, ready for the first breaking 2.0 change — the versioning policy this ships under (documented separately, in the prior Public API Review) requires exactly this split.
  • The two open value objects (DeviceCategory, ProtocolType) are explicitly marked experimental in the classification carried into this package, which is itself a SemVer-correct move: it reserves the right to adjust their shape within the 1.x line without violating the compatibility promise made to everything else.
05

Suitable for public release as v1.0.0 — no, but not for a code reason

Finding — the LICENSE file directly contradicts a public release

LICENSE reads: "This package is proprietary and confidential. It is distributed exclusively via Tanaki Hub's private Composer path repository for use by Tanaki Hub and its authorized integration partners. No part of this package may be reproduced, distributed, or published outside that context without prior written permission." composer.json matches: "license": "proprietary". Technically, nothing in the code prevents public release — it's genuinely portable, as every other section of this audit confirms. But the package as currently licensed legally forbids exactly the action being asked about. This is a business/legal decision, not an architectural one, and it's the single clearest way this audit could show "not suitable for public release" without finding a single line of coupling — which is precisely why an external maintainer, reading only what's on disk, would have to answer "no" to this specific question as asked, while still answering "yes" to every technical reusability question in §01–§04 and §06–§07.

If the intent is genuine public release, the fix is a license/business decision (swap to MIT, Apache-2.0, or another OSI license, update the LICENSE file and composer.json's license field, and decide whether "Tanaki Hub" attribution stays) — not a code change, and out of scope for this audit per the instruction not to modify anything.

06

Can it be consumed by a completely different Laravel application?

Yes, with no evidence to the contrary found. Nothing in the package registers a service provider, publishes a config file, expects a specific container binding, reads an environment variable, or assumes any Laravel version-specific behavior. A different Laravel app — Laravel 10, 11, or 12, since the floor is plain PHP 8.2 — would composer require it exactly as Tanaki Hub does and get working interfaces, DTOs, enums, events, an attribute, and exceptions with zero Tanaki-specific setup. The one caveat: if that application wants to persist DeviceCategory/ProtocolType on an Eloquent model, it needs its own CastsAttributes adapter, exactly as documented in this package's own UPGRADE.md — that's a deliberate, documented consequence of the package staying framework-free, not an oversight.

Verdict

I could not find an architectural violation. Every dependency, hidden-coupling, and circularity check came back clean under direct evidence — grep sweeps, a case-sensitive namespace/directory audit (the one class of bug that Windows development specifically hides), inspection of the package's own resolved dependency tree, and a live execution test in a Laravel-free process. The two findings that did surface are real but narrow: one is a leaky string in a single exception message, fixable in isolation without touching the package's shape; the other is a licensing decision that has nothing to do with whether the code itself is portable — and by every technical measure in this audit, it is. Package extraction achieved exactly what three prior review rounds were building toward: a genuinely reusable, framework-free contracts library, not merely a relocated one.
