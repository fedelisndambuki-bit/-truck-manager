02

The one required adapter

Everything above is a namespace-only change except one real design decision, surfaced here before implementation rather than discovered mid-move.

DeviceCategory/ProtocolType's Eloquent Castable conflicts with "zero Laravel dependency"

The Public API Review (twice) required tanaki/integration-contracts to have no Laravel dependency at all — "pure PHP." The SDK-stabilization pass then had DeviceCategory/ProtocolType implement Illuminate\Contracts\Database\Eloquent\Castable specifically so IntegratedDevice's $casts array needed zero changes. Both were correct decisions in their own phase — but they now collide: a truly pure-PHP package cannot implement a Laravel contract interface.

Resolution: the package versions of DeviceCategory/ProtocolType drop Castable entirely — zero Illuminate dependency, as originally promised. The cast logic moves to two new app-side classes, App\IntegrationEngine\Casts\DeviceCategoryCast and ProtocolTypeCast (implementing CastsAttributes directly), and IntegratedDevice.php's $casts array points at those instead of at the enum classes themselves. This is the one place this extraction touches application behavior beyond a bare import-path swap — declared here, before implementation, exactly as the instructions require.

This keeps the package's dependency graph to exactly php: ^8.2 and nesbot/carbon: ^3.0 — nothing else — which is the target state every prior review round has been building toward.

04

Rollback plan

Produced before implementation, as required. If any validation step in §06 fails, this is the exact recovery procedure — no improvisation.

  1. Stop immediately. Do not attempt a partial fix under pressure — that's how a recoverable failure becomes an unrecoverable one.
  2. Identify the failure boundary. Was it before or after old files were deleted (§Sequence step 9)? This determines which of the two recovery paths below applies.
  3. If old files have not been deleted yet (the safe majority of the window): revert composer.json's repositories/require entries, run composer update, and the app falls back to the original App\IntegrationEngine\* files untouched on disk. Any consumer file whose use statements were already repointed gets restored from the backup directory captured in §00.
  4. If old files have already been deleted (only happens after §06 passes green, so this path should never be needed — but if a later, unrelated step still fails): restore the entire backup directory's contents over the current app/IntegrationEngine, app/Models/IntegratedDevice.php, app/Listeners/Weighbridge/RecordWeighbridgeReading.php, and both composer files, then run composer update.
  5. Re-run the validation checklist (§06 of the follow-up report) against the restored state to confirm the rollback itself didn't introduce a new problem.
  6. Explain the cause in plain terms before attempting the fix again — per instruction, no automatic retry.
Why this order is safe

Old source files are deleted only as the second-to-last step, after every functional validation has already passed against the package-backed version running side-by-side with the untouched originals still on disk. There is no point in the sequence where the app depends on a half-migrated state without a complete, untouched fallback still present.
