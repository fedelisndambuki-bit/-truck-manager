Evolving the Integration Engine into a Composer-installable plugin ecosystem

A gap analysis and migration design for composer require tanaki/teltonika-driver to work with zero changes inside the main application — without rewriting, replacing, or breaking anything currently shipping.

Prepared byChief Software Architect SubjectTanaki Integration Engine StatusDesign only ConstraintZero breaking changes

The Integration Engine shipped and verified last phase — driver interfaces, protocol adapters, discovery, registry, health checks, retries, reconnect, events, queueing, one working driver — is the production foundation. Nothing here proposes rewriting it. This review answers one question precisely: what, specifically, blocks a third-party Composer package from becoming a driver today, and what is the smallest, safest set of changes that removes those blockers. Two concrete blockers were found (§1), a five-tier package graph resolves both without touching the engine's public behavior (§2–3), and the migration is sequenced so every phase ships independently and reversibly (§4).

01

Current architecture

Everything the engine does today lives inside the host application's own namespace. That's correct for a first phase — it's wrong as a foundation for distributable packages, for two specific, fixable reasons.

Fig. 1 — every box above compiles into one Composer root package. There is no seam a second package could attach to.

Blocker A — discovery only ever looks inside the host app

DriverDiscoveryService resolves its scan path as app_path('IntegrationEngine/Drivers') and, for every file it finds, reconstructs the class name by literally prepending App\IntegrationEngine\Drivers\. A package installed to vendor/tanaki/teltonika-driver/ is never visited by the scan, and even if the path were widened, the hardcoded namespace prefix would resolve to a class that doesn't exist.

Blocker B — the contracts a package would implement aren't a package

WeighbridgeDriverInterface, the DTOs, the events, the #[IntegrationDriver] attribute — all declared under App\IntegrationEngine\Contracts, the host application's own root namespace. A standalone package cannot reasonably implement an interface that lives inside the application consuming it; that's a circular dependency, not a plugin boundary.

Two findings that make the migration cheaper than it looks

1. Grepping the full codebase for every class under App\IntegrationEngine\* turns up exactly two references outside the engine itself: IntegratedDevice's enum casts, and the one Weighbridge listener's event import. Every other one of the ~55 files that reference these namespaces is the engine. The strict "business modules never touch hardware" boundary enforced last phase means a namespace migration's blast radius is almost perfectly self-contained.

2. DeviceRegistryInterface currently type-hints Illuminate\Support\Collection in two return types — the one place a Laravel Framework dependency leaked into what needs to become pure-PHP contracts. Small, but it has to be named and fixed, not discovered mid-extraction. Laravel's Dispatchable/InteractsWithSockets/SerializesModels traits on the nine event classes are the same category of issue at larger scale — see §4, Phase 1.

04

Migration strategy

Eight phases. Every phase is independently shippable, independently reversible, and leaves the previous phase's guarantee intact. Nothing here is "big bang."

PHASE 0

Extract tanaki/integration-contracts as a path package

Move Contracts/, DTOs/, Enums/, Events/, Attributes/, Exceptions/ into packages/tanaki/integration-contracts/ inside the same repository, with its own composer.json. The host app requires it via a Composer path repository (symlinked into vendor/) — same repo, same deploy, same CI, zero network dependency, fully reversible by deleting one composer.json entry. Fix the two Laravel leaks found in §1 here: swap Illuminate\Support\Collection return types for plain array, and replace the event classes' Dispatchable/InteractsWithSockets/SerializesModels traits with plain, trait-free value classes — the Laravel dispatch behavior moves to Core (Phase 1), not lost, relocated.

✓ App behavior identical. Only use statements change (mechanical, covered by the existing php -l + grep verification pattern). No DB, config, or command surface touched.
PHASE 1

Extract tanaki/integration-core as a path package

DeviceRegistry, DeviceDriverFactory, DriverDiscoveryService, AbstractDeviceDriver, ProcessDeviceReadingJob, IntegrationEngineServiceProvider move to packages/tanaki/integration-core/. This is where the Laravel-specific event dispatch bridge lives now — Core wraps each pure Contracts event value object in a thin Laravel event before calling event(), so App\Listeners\Weighbridge\RecordWeighbridgeReading's handle() signature does not change. Core also gains the DriverRegistrar helper introduced in §9, used by both the existing filesystem scanner and, from Phase 3 onward, every package driver's own service provider.

✓ Same singletons, same config keys, same 5 Artisan commands, same hourly schedule entry, same log channel. bootstrap/providers.php now points at Tanaki\IntegrationCore\Providers\IntegrationEngineServiceProvider instead of the App\ one — a one-line change.
PHASE 2

Extract protocol packages, lowest-risk first

TcpProtocolAdapter and UdpProtocolAdapter first — they already have zero Laravel dependency (raw ext-sockets calls), so extraction is a pure file move. WebSocketProtocolAdapter and MqttProtocolAdapter next — already thin wrappers over portable libraries. HttpProtocolAdapter last and with one real decision: keep the Laravel Http facade (pragmatic — Tanaki Hub and most early driver authors are Laravel apps) or swap to a PSR-18 client for maximum portability. Recommendation: PSR-18, because §"Architectural requirements" explicitly cites League/Flysystem as the model, and PSR-18 is what makes a driver installable in a non-Laravel PHP app later without asking. The six unimplemented protocols move as-is — they remain honest stubs, nothing about their behavior changes.

✓ ProtocolAdapterInterface itself does not change, so no driver written against it needs to change.
PHASE 3

Prove the package-driver path with one real package before building six

GenericHttpWeighbridgeDriver becomes tanaki/generic-http-driver — chosen deliberately because it's the one driver already verified end-to-end. It ships its own tiny GenericHttpDriverServiceProvider, declared in extra.laravel.providers, calling Core's DriverRegistrar::register(...) on boot. composer require tanaki/generic-http-driver is run against a real checkout of the app, and the exact same tinker sequence used to verify Phase 1 of the original engine (discover → list → install → simulate a reading → confirm a real WeighbridgeTicket row) is re-run against the package-installed version. This is the phase that either confirms the whole design or surfaces a problem — deliberately sequenced before any of the six named vendor drivers are attempted.

✓ The local filesystem scanner keeps working, unmodified, for any driver not extracted yet — both mechanisms are proven to coexist by construction, not by assertion.
PHASE 4

Plugin registry — package-level, distinct from device-level

New driver_packages table and DriverPackage model (§10), additive to — never replacing — IntegratedDevice. IntegratedDevice continues to mean "a physical device a company owns"; DriverPackage means "a driver, installed or not, enabled or not, in this environment." Every column in integrated_devices stays exactly as-is.

✓ Purely additive migration. No existing table altered.
PHASE 5

Capability index

DriverMetadataDTO gains a richer sibling, DriverManifest (§12) — additive fields, existing consumers of DriverMetadataDTO untouched. A CapabilityResolver in Core indexes installed drivers by capability tag, so a business module can ask "which installed device can report fuel level" without ever naming a vendor.

✓ New query surface only. Nothing that reads getCapabilities(): array today breaks — the return shape is unchanged, just newly indexed.
PHASE 6

Integration Console (admin UI)

New Filament cluster, read-mostly against data Phases 1–5 already produce. No engine changes required to ship this — it's a consumer of the registry, not a dependency of it.

PHASE 7

Marketplace data model (design only, per current instruction — no downloads)

A read-only feed the Console's Marketplace tab queries. Explicitly out of scope for execution until named.

05

Backward compatibility strategy

"Backward compatible" is being held to a specific, checkable definition here — not "nothing changes," but "nothing that anything outside the engine depends on changes."

SurfaceGuaranteeVerified by
DB schema (integrated_devices)UnchangedNo migration touches this table; new tables are additive
Artisan commands & signaturesUnchangedSame 5 commands, same options, same hourly schedule entry
config/integration-engine.php keysUnchangedNew keys are additive with defaults
WeighbridgeReadingCaptured → listener contractUnchangedRecordWeighbridgeReading::handle() signature untouched — Core's dispatch bridge absorbs the internal event-class relocation
Internal namespaces (App\IntegrationEngine\*)Will changeConfined to the ~55 files that are the engine, per the grep finding in §1 — nothing outside it references these paths except the 2 already-identified touchpoints, both updated in the same commit
Local first-party driver mechanismUnchanged behavior, relocated codePhase 3 re-runs the original verification suite against it after the move
Why path repositories, not immediate Packagist publication

Every extraction phase uses a Composer path repository — the "package" is a real, separately-namespaced, separately-tested directory, but it deploys inside the same repo and the same release as everything else, with a symlink into vendor/. This gets 100% of the architectural benefit (real package boundary, real dependency direction, real backward-compat pressure) with 0% of the release-coordination risk. Publishing to Packagist under the tanaki/ vendor name is a separate, later, non-technical decision — the code doesn't need to change when that happens.

Auto-discovery design — two mechanisms, one registry

Both mechanisms end at the same call: DeviceRegistry::register($vendorKey, $driverClass, $category). Nothing about the registry itself needs to change for a second discovery path to exist — it was always just an array mutation with no opinion about who calls it.

Plugin registry — package-level, additive to IntegratedDevice

A new concept, deliberately distinct from the device inventory built last phase: IntegratedDevice answers "which physical devices does this company own"; the new DriverPackage answers "which driver code is installed in this environment, and is it trusted to run." One company's IntegratedDevice row references a DriverPackage by vendor key; it never embeds driver code or version info itself, which is what makes the device row stable while drivers update independently.

11

Capability model

The rule extends one that was already true by construction in the original build — no business listener has ever imported a vendor name. This phase makes it queryable, not just accidentally true. A capability is a plain string tag on the manifest (supports_gps, supports_fuel_level, supports_engine_hours, supports_weighbridge, supports_biometrics, supports_rfid, supports_barcode, supports_qr, supports_can_bus, supports_plc, supports_mqtt, supports_offline_buffering, supports_live_streaming, supports_remote_configuration) — deliberately a flat, extensible list rather than an enum, so a driver package can declare a capability Core has never heard of without a Core release. A business module asks the CapabilityResolver for "any enabled device with supports_fuel_level" and gets back device IDs, never class names.

15

Marketplace — data model only, no downloads

Recommended shape: a curated feed, not a bespoke store — Composer packages typed "type": "tanaki-driver" in their own composer.json (Composer already supports arbitrary package types for exactly this kind of filtering), indexed the same way Packagist already indexes by type. The Console's Marketplace tab fetches that feed, renders each listing's manifest (name, manufacturer, capabilities, license, docs link), and — explicitly, per this instruction — stops there. The future "install from the UI" action is a single, well-scoped addition later: shell out to Composer (or its PHP API) with the selected package name, which is exactly why installation was designed as an ordinary composer require in every phase above rather than a custom mechanism — the marketplace has nothing special to build when that day comes, only a button to wire up.

Documentation plan

Outline for the third-party driver-authoring guide — full prose is a Phase 3+ deliverable (it needs the pilot package to exist first, so every example in it is real and copy-pasteable), but the structure is fixed now so nothing downstream is designed around documentation that doesn't exist yet:

  7. Passing contract tests — extending the shipped abstract test case
  8. Publishing — semver discipline against minimumCoreVersion, the tanaki-driver Composer package type for marketplace indexing
