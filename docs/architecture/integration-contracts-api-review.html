tanaki/integration-contracts — public API review and stability analysis

Every interface, DTO, enum, attribute, event, and exception that will ship in the pure-PHP contracts package, reviewed against the standard third-party publishing owns for years, not months.

Packagetanaki/integration-contracts Targetv1.0.0 Public types reviewed49 ExtractionBlocked until §07 clears

Package extraction (§04 of the prior migration plan) does not start from this document — it starts after every item on the §07 checklist is resolved. That ordering is deliberate: the architecture review approved the shape of the five-tier package graph; this review is about the one package in that graph where a mistake is nearly permanent. Once a hardware manufacturer's driver compiles against tanaki/integration-contracts:^1.0, every public signature in it is a promise Tanaki has to keep to code it doesn't own and can't recompile. Six concrete pre-freeze defects were found — three would be straightforward breaking changes if caught after 1.0, one (§Enums) is a structural blocker to the entire plugin-ecosystem goal. All six are free to fix now and are listed as blocking items in §07.

Core & category interfaces (16)

SOLID lens applied to all 16: Interface Segregation is the standout strength of the current design — DeviceDriverInterface composes three single-purpose interfaces (HealthCheckableInterface, DiagnosticsInterface, DriverMetadataInterface) rather than declaring one flat 8-method contract, so code that only needs a health probe can depend on a two-method interface instead of the whole driver surface. Dependency Inversion holds throughout: nothing in this layer references a concrete class. Liskov holds by construction — every category interface only adds methods to DeviceDriverInterface, never narrows or overrides one, so any category driver is safely substitutable wherever the base interface is expected. Single Responsibility is where the review found the one real inconsistency, noted under WeighbridgeDriverInterface below. Open/Closed is the throughline of the whole review: every interface is closed for modification by definition (it's about to be frozen) — the open questions are all about whether each one was designed to be extended correctly before that happens.

DeviceDriverInterfaceStable

The contract every driver implements regardless of vendor or category — lifecycle plus composition root for the three focused sub-interfaces.

Extensible: yes — extended by 9 category interfaces, the intended path Inheritance: interface inheritance only; implementers must not be required to extend a base class (see §SDK Guide, composition over inheritance) Composition: composes 3 segregated interfaces rather than declaring their methods directly — correct, keep

VersioningAdding a method here is binary- and source-breaking for every existing driver package, local or third-party — it is the single highest-blast-radius type in the package. Post-1.0, new lifecycle behavior must ship as a new opt-in interface (e.g. PausableDriverInterface) that drivers may additionally implement, never as an addition to this one.

HealthCheckableInterface / DiagnosticsInterface / DriverMetadataInterfaceStable

The three segregated pieces DeviceDriverInterface composes — one method each (healthCheck(), runDiagnostics(), getMetadata()+getCapabilities()). Reviewed together: same verdict applies to all three.

Extensible: yes, by design — this is why they're separate from the base interface Composition: preferred and already applied

Source compatDriverMetadataInterface::getCapabilities(): array returns untyped string[] rather than the enum-like capability tags this whole ecosystem is meant to standardize on. Low risk today (it's additive-safe either way), but worth deciding in §Extension Guide whether capability strings get a validated vocabulary before third parties start inventing their own spellings of supports_gps.

ProtocolAdapterInterfaceStable

Transport-level contract, deliberately independent of vendor payload interpretation (Strategy pattern — adapters are interchangeable per protocol, drivers compose one).

Extensible: yes, one adapter per protocol package Inheritance: not used — flat implementation, correct

Design notesend()/receive() return mixed deliberately — protocol-level payloads are inherently untyped until a driver interprets them. Correct as designed; documented here so it isn't "fixed" into something narrower during extraction, which would break every adapter package.

DeviceRegistryInterfaceStable after fix

Lookup contract for "which driver class handles this vendor key" — consumed by Core's internals and by any admin/business code (e.g. a future Filament resource) that wants to query installed drivers without depending on the concrete DeviceRegistry class.

Belongs in Contracts: yes — kept here rather than moved to Core, so consumers can depend on the interface (Dependency Inversion), not Core's concretion

Binary compat — blockingdriversForCategory() and all() return Illuminate\Support\Collection — a Laravel Framework dependency inside a package that must build without Laravel. This is the interface-level instance of the leak flagged in the architecture review. Fix required before freeze: change both return types to array. This is a source-breaking change for any caller currently chaining Collection methods (->pluck(), ->filter()) on the result — cheap now, effectively impossible once a third party has written code against the Collection-returning signature.

DriverFactoryInterfaceStable

Resolves and constructs a driver instance from a vendor key via the container, so a driver's own constructor dependencies still get injected normally.

Single method: make(string $vendorKey): DeviceDriverInterface — minimal, nothing to segregate further

Future expansionNo tryMake(): ?DeviceDriverInterface non-throwing variant exists yet. Not a defect — make() throwing DriverNotFoundException is a reasonable default — but if a non-throwing lookup is ever needed, it must be a new method on a new interface (e.g. a NullableDriverFactoryInterface), never a signature change here.

The 9 category interfacesStable, one rename pending

WeighbridgeDriverInterface, GpsTrackerDriverInterface, FuelControllerDriverInterface, RfidReaderDriverInterface, BiometricDriverInterface, BarcodeScannerDriverInterface, QrReaderDriverInterface, PlcDriverInterface, IotSensorDriverInterface — each extends DeviceDriverInterface and adds exactly the parse method(s) its category needs. Reviewed as a family: near-identical shape is a strength here (a manufacturer learns the pattern once), not duplication worth abstracting further — collapsing them into one generic parse(array): mixed method would destroy the compile-time type safety that's the entire point of standardizing per-category DTOs.

Data transfer objects (12)

9 category-reading DTOs (WeighbridgeReadingDTO, GpsPositionDTO, FuelTransactionDTO, RfidScanDTO, BiometricEventDTO, BarcodeScanDTO, QrScanDTO, PlcSignalDTO, SensorReadingDTO) plus DeviceHealthDTO, DeviceDiagnosticsDTO, and DriverMetadataDTO. Every one is final readonly class with constructor-promoted properties — this is exactly right for a value object crossing a package boundary: final removes any Liskov risk from third-party subclassing, and readonly makes the immutability guarantee compiler-enforced, not a convention.

Immutability defect — blocking

All 12 DTOs type their timestamp fields as Carbon\Carbon — the mutable Carbon class. readonly only prevents reassigning the property; it does not stop $reading->capturedAt->addDay() from mutating the shared Carbon object in place, silently corrupting a value object every consumer assumes is frozen. Fix: switch every DTO's timestamp property to Carbon\CarbonImmutable — a drop-in, API-compatible swap (all read methods are identical; only the mutator methods now return new instances instead of mutating). Free before 1.0; after 1.0 it's technically source-compatible but is a real behavior change some consumer could be inadvertently depending on, which makes it exactly the kind of fix that belongs in a pre-freeze review rather than a point release.

Dependency — blocking

nesbot/carbon is used directly in every DTO but is not a direct Composer dependency anywhere in the current codebase — it's pulled in transitively via laravel/framework. A pure-PHP package cannot rely on a transitive dependency of an application that may not always be Laravel. tanaki/integration-contracts must declare "nesbot/carbon": "^3.0" explicitly in its own composer.json.

Structural evolution risk (all 12): constructor-promoted properties are positional as well as named. Nothing in the current codebase constructs a DTO positionally today (verified by usage), but nothing prevents a third party from doing so once these ship publicly. Policy for §03: every future DTO field addition must be appended at the end of the constructor with a default value — inserting a field in the middle, even an optional one, silently breaks positional-argument callers. Named-argument construction should be the documented, recommended convention in §05 specifically to make this policy low-risk in practice.

Enumerations (4)

Structural blocker to the plugin-ecosystem goal — highest priority in this entire review

DeviceCategory and ProtocolType are native PHP backed enums. Native enums are closed — PHP has no enum inheritance, and a third-party package cannot add a case to an enum it doesn't own. This directly contradicts the stated goal of the plugin ecosystem: a manufacturer building a CCTV, AI-camera, or PLC-variant driver that doesn't fit the 9 existing categories has no legal value to return from getCategory(): DeviceCategory, and Tanaki would have to cut a new Contracts release for every category the ecosystem wants to grow into — recreating, at the taxonomy level, exactly the central bottleneck this whole initiative exists to remove.

Recommendation: before freeze, convert DeviceCategory and ProtocolType from native enums into extensible value objects — final readonly class with a private constructor, named static factories for the known built-in cases (DeviceCategory::weighbridge() replacing DeviceCategory::Weighbridge), and a public DeviceCategory::custom(string $key, string $label): self escape hatch, compared by ->equals() rather than ===/match. This is the same shape Doctrine and Flysystem use for open-ended taxonomies precisely because native enums can't do it. The trade-off is real and worth stating plainly: it gives up native match exhaustiveness and ::cases() reflection. DeviceStatus and ConnectionMedium do not need this treatment — device lifecycle state and link-layer medium are closed sets by nature, not something a manufacturer needs to extend, and keeping them as simple native enums is correct.

Dependency — blocking

All 4 enums implement Filament\Support\Contracts\HasLabel — a UI-framework dependency inside a contract a hardware manufacturer implements against. A driver author has no reason to have Filament installed. Fix: strip HasLabel/getLabel() from all 4 enums in Contracts. Label presentation moves to the application layer (an app-side lookup/match, or explicit ->options() callbacks on the Filament form/table components that currently free-ride on auto-detection). This is a small, mechanical, one-time migration cost inside Tanaki Hub itself — worth paying now, because removing an interface from a public enum after 1.0 is a binary-breaking change for any driver package that does instanceof HasLabel.

Versioning note for the two kept as native enums: adding a new case to a closed backed enum is source-compatible for consumers matching on individual cases, but is binary/behavior-breaking for any match expression without a default arm — UnhandledMatchError at runtime the moment the new case reaches old code. §05 must instruct driver authors to always include a default arm when matching on DeviceStatus/ConnectionMedium, and §03 must classify "add an enum case" as a minor-version change, never a patch.

Event contracts (12)

9 data events (one per reading DTO, e.g. WeighbridgeReadingCaptured) + DeviceCameOnline, DeviceWentOffline, DeviceHealthCheckFailed.

Dependency — blocking, verified zero-behavior-change fix

All 12 event classes use one or more of Illuminate\Foundation\Events\Dispatchable, Illuminate\Broadcasting\InteractsWithSockets, Illuminate\Queue\SerializesModels — three Laravel Framework traits baked into what needs to be a pure-PHP data contract. Checked against actual usage, not assumption: a repo-wide search found zero call sites using any event's static ::dispatch() sugar — the sole real dispatch path, ProcessDeviceReadingJob::handle(), calls the plain event(new $this->eventClass($this->dto)), which accepts any object. No event implements ShouldBroadcast, so InteractsWithSockets' broadcast-channel resolution is never exercised. No event carries an Eloquent model (they carry DTOs), so SerializesModels has nothing to rehydrate. All three traits can be removed from all 12 events with zero runtime behavior change — this was verified against the actual call site, not inferred. The Laravel dispatch convenience these traits provided moves to Core, which already owns the one call site that constructs and fires these events.

Design gap — recommended fix before freeze

DeviceCameOnline and DeviceWentOffline carry only string $vendorKey — the driver type, not the specific device instance, and no timestamp. A company running two Teltonika GPS units gets an indistinguishable DeviceWentOffline('teltonika') regardless of which one dropped, and a listener has no occurredAt to record. Adding string $deviceId and CarbonImmutable $occurredAt to both constructors now is additive-in-spirit but is still a constructor signature change — free today (nothing external depends on it yet), a breaking change the moment a third party's listener is written against the current two-argument-free shape.

Attribute (1)

#[IntegrationDriver]Stable after fix

Tags a driver class for discovery and is the single source of truth for its metadata — AbstractDeviceDriver::getMetadata() reads it back via reflection rather than requiring drivers to redeclare the same facts twice.

Target: TARGET_CLASS only — correct, an attribute per method/property was never needed here

Consistency — blockingAll 6 constructor-promoted properties are plain public, not readonly — the one immutability inconsistency in the whole package, next to 12 DTOs that are all correctly readonly. An attribute instance is built once by Reflection and never legitimately mutated afterward; mark all 6 properties readonly before freeze (zero behavior change, since nothing currently mutates them). Versioning3 of 6 constructor parameters have defaults (version, capabilities, displayName/description); any future parameter must be appended with a default for the same reason as the DTOs — PHP attribute arguments are an ordinary constructor call.

Exceptions (4)

DeviceOfflineException, DriverNotFoundException, InvalidPayloadException, ProtocolNotImplementedException — each extends RuntimeException directly, each with a named static constructor (::forDevice(), ::forVendor(), etc.) rather than a public __construct(), which is good practice: it keeps the message format an implementation detail instead of a signature third parties depend on positionally.

Hierarchy gap — recommended addition before freeze

There is no common Tanaki-specific type to catch. A third-party driver author who wants to catch "any failure originating from the integration layer" today can only catch RuntimeException, which is far too broad — it would also catch unrelated exceptions from their own code in the same try block. PHP has no multiple class inheritance, so the fix isn't a shared base class; it's a marker interface (the pattern Doctrine, Guzzle, and Symfony all use for exactly this): add IntegrationExceptionInterface extends \Throwable, have all 4 exceptions implement it. Purely additive, zero risk, but must exist from 1.0.0 — adding it later means pre-existing exception classes gain an interface, which is binary-safe but fragments "some Tanaki exceptions are catchable via the marker, some aren't" during the gap.

Stability classification

Every type gets one of five labels going into 1.0. Stable: frozen shape, changes only via the versioning rules in §03. Extension Point: stable, and specifically the interface/type a third party is expected to implement or extend. Internal: public visibility for technical reasons (cross-namespace access within Contracts) but never meant for outside use. Singular segment names (Contract, DTO, Enum, Event, Exception) rather than the current plurals — matches PSR-4 convention in League/Symfony packages and drops the redundant "Contracts" folder living one level inside a package that is itself named contracts.

Naming conventions ratified for 1.0

  • Category interfaces: {Category}DriverInterface, single parse method named parseX(): XDTO — see the captureWeight rename above.
  • DTOs: {Noun}DTO, always final readonly class, always end with array $rawVendorPayload = [].
  • Events: past-tense, {Noun}{PastTenseVerb}.
  • Exceptions: {Failure}Exception, named static constructors only, no public general-purpose constructor.

Composition over inheritance — the rule, not just a preference

Every extension point in this package is an interface, not an abstract class. Contracts ships zero abstract classes on purpose: an abstract base class in a versioned public package is a much sharper compatibility hazard than an interface, because adding a method to an abstract class either breaks every subclass (if declared abstract) or is silently inheritable (if concrete) in a way that's easy to get wrong across a major-version boundary. AbstractDeviceDriver stays exactly where it is — in tanaki/integration-core, a convenience base class Tanaki controls the versioning of, that drivers may use but are never required to extend, since they only have to satisfy the interfaces in Contracts.

03

Versioning strategy

Standard SemVer 2.0.0, with explicit rulings on the PHP-specific edge cases that generic SemVer guidance glosses over — interfaces, enums, and attributes each break differently than classes.

ChangeBumpReasoning
Add a method to any interfaceMajorBreaks every existing implementer — binary and source breaking
Add a new interface (extension point)MinorPurely additive; nothing depends on it yet
Add an optional constructor parameter (with default) to a DTO/Attribute, appended lastMinorSource-compatible for named-argument and existing positional callers
Add a required constructor parameter, or insert one before the endMajorBreaks positional construction — forbidden pre-1.0 fix; disallowed entirely post-1.0 without a major bump
Add a case to a closed native enum (DeviceStatus, ConnectionMedium)Minor, documented loudlySource-safe, but breaks any match without a default arm — release notes must call this out explicitly every time
Add a named factory case to DeviceCategory/ProtocolType (open value objects)MinorPurely additive by design — this is the entire reason they were converted
Add a new event classMinorAdditive; existing listeners unaffected
Change an event constructor signatureMajorBreaks any code constructing the event directly (tests, simulators)
Add a new exception class implementing IntegrationExceptionInterfaceMinorAdditive; interface-level catches remain valid
Narrow a return type or widen a parameter typeMajorPHP variance rules make this backward-incompatible for implementers even though it looks like a narrowing "improvement"
Widen a return type or narrow a parameter type (covariant/contravariant-safe direction)Minor, case-by-caseOnly safe if no implementer's override becomes invalid — verify against real driver code, not just theory, before shipping
Bump the PHP version floorMajorCan silently drop support for an installed base
Documentation, PHPDoc, internal formattingPatchNo compiled-code effect

Deprecation policy

  1. A type or method is never removed in a minor release — only in the next major.
  2. Deprecation is announced at least one full minor version before the removing major — e.g. a method deprecated in 1.4 cannot be removed before 2.0, and 1.4's release notes must state the planned removal version.
  3. Deprecated symbols get PHP's native #[\Deprecated] attribute (8.4+) or a PHPDoc @deprecated tag plus a trigger_error(..., E_USER_DEPRECATED) for earlier 8.2/8.3 support, so IDEs and CI both surface it.
  4. Every deprecation entry in the changelog states the replacement API, not just that the old one is going away.

Minimum support window

Once 2.0 ships, 1.x receives security and critical-bugfix patches for a minimum of 12 months — long enough that a hardware manufacturer on a slow release cadence isn't forced into an emergency major-version migration.

Extension guide

What a third party is meant to build against, and what they should never reach for.

You are building…ImplementNever

Why events are not an open extension point in 1.0

The 12 shipped events cover every category interface plus lifecycle. Letting third parties define arbitrary new event classes would mean business-side listeners in Tanaki Hub (and any other consuming app) would need to discover and subscribe to event classes they've never heard of — the opposite of the "business modules never know the vendor" principle this whole engine was built on. If a genuinely new event category is needed, it ships as a Tanaki-authored minor-version addition, informed by real third-party requests, not authored ad hoc per package.

Contract test suite (design, not implementation)

Each category interface should ship an abstract PHPUnit test case in Contracts itself (e.g. WeighbridgeDriverContractTestCase) that a manufacturer extends and points at their own driver — the same pattern league/flysystem-adapter-test-utilities uses. This lets a driver prove conformance without ever seeing Tanaki's own driver implementations, and gives Tanaki a mechanical way to verify a proposed interface change doesn't silently break the contract's own stated guarantees. Building the actual test cases is implementation work, out of scope for this document — recorded here so it's on the v1.0 checklist.

06

Architecture decision records

One ADR per real decision point, not one per type — 9 near-identical category interfaces share a single ADR (ADR-0003) rather than 9 rubber-stamped copies; decisions genuinely unique to one type get their own record.

ADR-0001
Segregate the driver contract into four interfaces instead of one
Accepted
Context

A single flat DeviceDriverInterface with 8+ methods would force every consumer — including code that only ever health-checks a device — to depend on the entire surface.

Decision

Split into HealthCheckableInterface, DiagnosticsInterface, DriverMetadataInterface, composed by DeviceDriverInterface.

Consequences

Every real driver still implements all four; the benefit is entirely on the consuming side (narrow type-hints) and for future extension points that can compose a subset.

Status

Already correctly implemented — ratified as-is, no change required.

ADR-0002
DeviceRegistryInterface returns array, not Illuminate\Support\Collection
Proposed
Context

driversForCategory()/all() currently type-hint Collection, the only Laravel Framework dependency remaining in the interface layer.

Decision

Change both return types to plain array. Callers who want Collection ergonomics wrap the result themselves (collect($registry->all())) — free in a Laravel consumer, no-op cost in a non-Laravel one.

Consequences

Source-breaking for the two existing internal call sites (mechanical fix); removes the last framework dependency from this interface.

Alternatives considered

Move the interface to Core instead of Contracts — rejected: business/admin code should be able to depend on the registry contract via Dependency Inversion without depending on Core's concrete implementation.

ADR-0003
Category interfaces follow parseX(array): XDTO; WeighbridgeDriverInterface renamed to match
Proposed
Context

8 of 9 category interfaces already follow a consistent parseX() convention; captureWeight() is a same-shape outlier with no functional justification.

Decision

Rename to parseReading(array $rawPayload): WeighbridgeReadingDTO before 1.0.0.

Consequences

Breaks the one existing first-party driver (mechanical one-line fix); prevents a permanent naming wart in a frozen interface.

ADR-0004
DeviceCategory and ProtocolType become open value objects, not native enums
Proposed
Context

Native PHP enums cannot be extended by third-party code. The plugin ecosystem's core premise is that manufacturers can add hardware support without a Tanaki release.

Decision

final readonly class with private constructor, named static factories for built-in cases, and a public custom(string $key, string $label): self factory. DeviceStatus and ConnectionMedium remain native enums — their sets are closed by nature.

Consequences

Loses native match exhaustiveness checking and ::cases() reflection for these two types specifically; gains genuine third-party extensibility, which is the more important property for these two specifically.

Alternatives considered

Add an Other case plus a free-text sibling field — rejected as a leaky, harder-to-query half-measure compared to a proper open value object.

ADR-0005
Enums (and all Contracts types) drop the Filament HasLabel dependency
Proposed
Context

All 4 enums implement Filament\Support\Contracts\HasLabel, pulling a UI framework into a package hardware manufacturers build against.

Decision

Remove HasLabel/getLabel() from Contracts entirely; label presentation becomes an app-layer concern in Tanaki Hub.

Consequences

One-time mechanical migration inside the app wherever Filament auto-detected labels from these enums; permanently removes Contracts' only UI-framework dependency.

ADR-0006
Event contracts ship as plain PHP objects; Laravel dispatch traits removed
Proposed
Context

12 event classes carry Dispatchable/InteractsWithSockets/SerializesModels. Verified against the one real dispatch call site (ProcessDeviceReadingJob, which calls plain event()): none of the three traits' behavior is exercised anywhere in the codebase today.

Decision

Strip all three traits from all 12 events. DeviceCameOnline/DeviceWentOffline additionally gain string $deviceId and CarbonImmutable $occurredAt constructor parameters.

Consequences

Verified zero runtime behavior change for the trait removal. The two new constructor parameters are a breaking signature change, applied now while free rather than after third parties construct these events directly (e.g. in simulators/tests).

ADR-0007
All 12 DTOs use CarbonImmutable, not Carbon
Proposed
Context

readonly on a DTO property prevents reassignment but not mutation of the mutable Carbon object it points to — an immutability gap at the object-graph level.

Decision

Type every DTO timestamp property as Carbon\CarbonImmutable; declare nesbot/carbon as a direct dependency rather than relying on Laravel's transitive install.

Consequences

API-compatible for every read-only usage found in the codebase (identical method surface); any code relying on in-place mutation, if it exists, would need to switch to reassignment — none was found.

ADR-0008
#[IntegrationDriver] attribute properties become readonly
Proposed
Context

The attribute's 6 constructor-promoted properties are plain public, inconsistent with the readonly guarantee every DTO in the package carries.

Decision

Mark all 6 readonly.

Consequences

Zero behavior change — nothing currently mutates an attribute instance post-reflection.

ADR-0009
Introduce IntegrationExceptionInterface as a catch-all marker
Proposed
Context

4 exceptions each extend RuntimeException directly with no common Tanaki-specific supertype; PHP has no multiple class inheritance.

Decision

Add a marker interface extending \Throwable; all 4 exceptions implement it, effective from 1.0.0.

Consequences

Purely additive. Must ship at 1.0.0 rather than a later minor, so no exception type ever exists without it.

ADR-0010
Contracts declares zero abstract classes — composition-only extension points
Accepted
Context

An abstract base class in a versioned public package is harder to evolve safely than an interface — adding a concrete method is fine, but the temptation to add abstract methods (which breaks every subclass) is a standing hazard.

Decision

Every extension point in Contracts is an interface. AbstractDeviceDriver stays in Core as an optional convenience, never a requirement.

Consequences

Already the current design — ratified, not changed.
