04

Newly discovered concerns

Found only while implementing, not visible from the paper review. Two were resolved as part of this pass; one is a real gap, honestly disclosed rather than hidden.

Resolved during implementation — PHP attribute constant-expression restriction

The original ADR-0004 design assumed DeviceCategory could be instantiated inline inside #[IntegrationDriver(category: DeviceCategory::weighbridge())]. PHP attribute arguments must be constant expressions — a static method call is not one, even under the PHP 8.1 "new in initializers" extension (which permits new Foo(), not arbitrary method calls). This would have silently broken driver auto-discovery. Resolution: built-in categories are exposed as public class constants (DeviceCategory::WEIGHBRIDGE) — a class-constant fetch, which is a valid constant expression — and the attribute now carries the raw string, converted to the rich value object via DeviceCategory::from() at the point of use. Same extensibility goal, same IDE-autocomplete safety for built-ins, verified working against the real shipped driver.

Honestly disclosed, not fully resolved — DeviceCameOnline/WentOffline's deviceId is a stand-in

The API shape now carries string $deviceId as requested. But AbstractDeviceDriver is resolved per vendor key, not per specific IntegratedDevice database row — it has no way to know which physical device instance is transitioning if a company runs two units of the same vendor. The two call sites in AbstractDeviceDriver::withAutoReconnect() currently pass getVendorKey() for both $vendorKey and $deviceId, with an inline comment explaining this. The contract shape is frozen correctly; the underlying data is not yet fully wired. Making drivers instance-aware is Core-layer work — out of scope for a Contracts-only stabilization pass, and not one of the 9 approved ADRs. Recommend tracking as a follow-up before this event is relied on to distinguish between same-vendor devices in production.

Pre-existing, unrelated — repo-wide RefreshDatabase test failures

4 of the new tests (the two Eloquent-cast persistence tests and two pipeline tests using RefreshDatabase) fail with SQLSTATE[HY000]: no such table: payouts. Confirmed via a control run that this is not caused by this work: an existing, untouched test (TripObserverTest) fails with the identical error. Something in the full migration sequence has an ordering dependency that breaks a from-scratch SQLite run. The equivalent logic was independently verified working via a live transaction-rolled-back script against the real database connection (§02) — the failure is confined to the from-scratch migration path, not the code under test. Flagging for awareness; fixing it is outside this review's scope.
